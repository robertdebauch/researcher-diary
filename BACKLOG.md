## 1. Ждёт внешних условий

- **[ ] CARTO basemaps** — ждём ключ (заявка отправлена Робертом). Когда ключ есть:
  - `light_nolabels` по умолчанию (чистая карта), переключатель на `light_all` (подписи);
  - атрибуция «© OpenStreetMap contributors, © CARTO» **видимая**, без флага Leaflet (`AttributionControl prefix={false}`);
  - ключ в `.env.local` (`VITE_CARTO_KEY`), ограничение по домену в их дашборде;
  - без ключа — фолбэк на OSM-тайлы, приложение не ломается.
- **[ ] Распознавание фото (Gemini API)** — ждём ключ Роберта. Free tier: 60 RPM / 100K TPM / 100 RPD, сброс RPD в полночь по PT (11:00 МСК). План: `recognizeImage()` с моком → один реальный вызов на фото → UX. Обязательно: счётчик «сегодня N из 100», предупреждение на 80%, обработка 429, кэш по хешу фото, отправка уменьшенной копии (~768 px), результат в `finding.recognition`.

## 2. UX и надёжность (ключи не нужны)

- **[ ] Журнальная подача находки** **[Р]** — заметка пишется под вопрос «Что вы нашли?» в винительном падеже («синюю шубу»), и в карточке это читается криво. Варианты: **(а)** добавить в карточку связку «в 18:37 я нашёл …» и оставить одно поле; **(б)** разделить на два поля — «название» (именительный: «Синяя шуба») и «описание» (подробности или пусто). Вариант (б) заодно даёт место для результата распознавания — сейчас непонятно, куда API будет класть описание.
- **[ ] Убрать дубль счётчика находок в отчёте** — обсудить. Сейчас число есть в таблице («3 / находки») и повторяется подписью секции («3 находки · …»). Предложение: счётчик оставить в таблице, подпись секции сократить до «НАХОДКИ». Решение по месту — за Робертом.
- **[ ] Кнопки «отчёт» и «удалить»** — стоят рядом и одного цвета. Сначала решить **куда** их разнести (второй ряд, меню строки, только в отчёте), потом двигать; правила UI-скиллов могут расходиться с редукционистской концепцией — сверять с §9.
